# AresaDB v2.0.0-alpha.2

> Multi-Raft + range-sharded cluster, a replicated placement driver,
> range leader leases, and an opt-in fjall-backed LSM engine —
> alongside the single-binary embedded engine that's been AresaDB's
> bread and butter since v0.2.

This is the second alpha of the v2 distributed stack. The v1 embedded
engine that the technical report describes is unchanged on its user-
facing surface (and is in fact ~2× faster at batch inserts than the
0.2.0-dev baseline, thanks to incidental cleanup during the Phase 2
refactors); everything *new* below is the v2 cluster that now lives
alongside it in the same repo.

**Status.** Alpha. Known limitations are listed in
[`docs/operations.md` §8](./docs/operations.md). The `v2.0.0-alpha.2`
tag is meant for operators experimenting with the distributed surface,
for CI coverage in downstream projects that depend on the crate, and
for the publication pipeline that will ship a dedicated v2 companion
tech note alongside the existing v1 paper.

## What's new

### Distributed runtime

- **Multi-Raft per node** — `aresadb-raft` wraps openraft 0.9 with a
  typed log / snapshot layout and a `SingleNode` harness for tests and
  benches. One Raft group per range, multiplexed across one gRPC port
  per node via a new `raft_group_id` envelope in the wire protocol.
- **Range-aware `ClusterNode`** — `aresadb-cluster` now owns a
  `RangeDirectory` keyed by range id. Each range gets its own
  `RangeRuntime` that bundles the Raft group, the log backend (always
  redb), and the data backend (redb or fjall). Admin RPCs for
  `AddRange`, `RemoveRange`, and `ListRanges` go through a single
  gRPC server; per-range fan-out lives in the `RaftDirectory` trait.
- **Placement driver** — `aresadb-pd` is a new workspace crate that
  runs as its own 3-node Raft group, owns the authoritative catalog
  (range descriptors, leases, node info), and serves an admin gRPC
  surface (`pd_status`, `list-ranges`, `create-range`, `split-range`,
  `merge-range`, `update-lease`, `heartbeat`) plus a `HeartbeatLoop`
  background task consumed by every cluster node's `pd_supervisor`.
- **Range leader leases** — `linearizable_get` on the leader
  (ReadIndex + lease), `stale_get` on followers, typed `ReadError` for
  NotLeader / ForwardToLeader. Admin `Read` RPC gains a
  `ReadConsistency` enum and an optional `range_id`.

### Storage plane

- **Unified keyspace** — `aresadb-core::keys` ships the canonical
  encoder / decoder for the v2 byte-sorted keyspace (§3.1 of
  `docs/architecture-v2.md`). One keyspace for every model: `/n/`,
  `/i/`, `/e/`, `/ef/`, `/et/`, `/p/`, `/ft/`, `/v/`, `/s/`, `/x/`,
  `/m/`. Variable-length segments use CRDB-style escape encoding.
- **Opt-in fjall LSM engine** — `aresadb-engine-lsm` implements
  `StorageBackend` on fjall's `Keyspace` + `Partition`. Opt-in per
  node via `NodeConfig::with_data_engine(DataEngine::Lsm)`. The Raft
  log stays on redb — single-writer, append-heavy, fsync-per-commit
  is redb's sweet spot. Conformance parity with the default redb
  backend is enforced by a shared test battery.

### Operator surface

- **`aresadb-cluster` CLI** — `bootstrap`, `join`, `add-voter`,
  `change-membership`, `write`, `read` (`--consistency
  {linearizable,stale,unspecified}` + `--range-id`), `status`,
  `add-range`, `remove-range`, `list-ranges`, and a full `pd`
  subcommand group. See [`docs/operations.md`](./docs/operations.md)
  for the operator runbook.
- **3-node Docker Compose smoke** — `docker/cluster/` ships a
  production-shaped 3-node stack with real hostnames, real on-disk
  redb volumes, and `bootstrap.sh` + `multi-range.sh` scripts that
  exercise the Phase 1 admin surface and the Phase 2c-6 range-aware
  surface end-to-end. The new `.github/workflows/docker-smoke.yml`
  runs both scripts nightly on GHA runners.

### Benchmarks & publications

- **v1 embedded benchmarks re-run** on the alpha.2 workspace
  (2026-04-20). The v1 paper's numbers are preserved — batch insert
  actually improved from ~38K to ~75K nodes/sec. Fresh JSON archived
  at [`benchmarks/results-2026-04-20-alpha2.json`](./benchmarks/results-2026-04-20-alpha2.json).
- **`benches/v2_cluster_bench.rs`** — new Criterion harness for the
  v2 distributed stack. Tracks today: `raft/apply_single_node/put_{one,batched/16,batched/128}`
  and `engine/backend/{put,put_batched/64,get_warm,scan_range}/{redb,fjall}`.
  Smoke numbers + takeaways in [`docs/publishing-audit.md`](./docs/publishing-audit.md)
  §4a. The legacy `distributed_bench.rs` stays for compile coverage
  of the v0.2-era utility module but is explicitly scoped as NOT on
  the v2 data path.
- **Publishing audit** — [`docs/publishing-audit.md`](./docs/publishing-audit.md)
  reconciles the v1 embedded paper with the v2 cluster, documents
  the re-run, and enumerates the follow-up tracks (sized v2 bench,
  v2 companion tech note, v1 Zenodo upload, v1 §8 conclusion edit —
  the last of which landed in this release).

## Breaking changes

This is an alpha release in a major-version bump line, so "breaking
changes" is the default expectation. The surfaces most likely to
affect downstream consumers:

- **Workspace split.** The repo is now a Cargo workspace; the root
  `aresadb` crate retains its embedded-engine API unchanged, but the
  new v2 crates (`aresadb-core`, `aresadb-raft`, `aresadb-pd`,
  `aresadb-net`, `aresadb-cluster`, `aresadb-engine-redb`,
  `aresadb-engine-lsm`, `aresadb-sim`) are `publish = false` — they
  evolve with `v2.0.0-alpha.*` and are not stabilised yet.
- **`src/distributed/wal.rs` removed.** The v1 WAL stub is gone; the
  real replication log is in `aresadb-raft`. If you imported the WAL
  types directly, they are no longer part of the public API.
- **Docker image** — the v2 cluster now ships as
  `ghcr.io/yoreai/aresadb/cluster:2.0.0-alpha.2` (separate from the v1
  embedded CLI image at `ghcr.io/yoreai/aresadb`). It runs
  `aresadb-cluster` as the default entrypoint. The embedded engine is
  still on crates.io as `aresadb = "2.0.0-alpha.2"`.

The Python package (`aresadb-python` on PyPI) keeps its v1 API.

## Known limitations

From [`docs/operations.md` §8](./docs/operations.md):

- Single region, single tenant.
- No distributed query router (Phase 3).
- No MVCC or cross-range transactions (Phase 4).
- Range replication on the admin wire is single-voter by default;
  multi-voter ranges require the PD supervisor loop.
- Raft log is always on redb (by design).
- No in-place upgrade from v1 embedded to a v2 cluster; migrate via
  `StorageEngine::scan` + the admin `Write` RPC.
- No Jepsen-grade linearizability runs yet; deterministic simulation
  in `aresadb-sim` covers the current phase's correctness properties.

## Upgrade guide

### From v1 (embedded, `< 2.0.0-alpha.*`)

If you're using the embedded API (`aresadb::StorageEngine`, property
graph operations, HNSW, BM25 etc.), no code change is required. Bump
the `aresadb` dependency to `"2.0.0-alpha.2"`; the embedded surface
is source-compatible with the v0.2 line.

If you were using the (now removed) `src/distributed/wal.rs` stub for
anything real, move to `aresadb-raft` — it's a fully-wired openraft
log storage and exposes the same write-ahead semantics with real
replication.

### From `v2.0.0-alpha.1`

All `v2.0.0-alpha.1` workspace crates are replaced by `-alpha.2`
variants. Nothing stabilised between the two alphas — every change in
the CHANGELOG between `[2.0.0-alpha.1]` and `[2.0.0-alpha.2]` is a
candidate break. Operators running alpha.1 clusters should wipe data
directories and re-bootstrap; we do not promise forward compatibility
within the alpha line.

### Post-tag portability follow-up (2026-04-20)

The first tag-driven Docker publish produced an image that worked
on Linux runners but failed its healthcheck on Docker Desktop for
Mac/Windows — the runtime dropped to `USER aresadb` at build time
but the named-volume mount materialised as `root:root` on Docker
Desktop, leaving redb / fjall unable to write. The fix landed as
back-compatible release-pipeline follow-ups on `main` and was
republished to GHCR at the same `:2.0.0-alpha.2` tag (new digest
above). The image now runs `docker-entrypoint.sh` under `tini`,
chowns the data directory at startup, and drops to the `aresadb`
user via `gosu` before exec'ing the binary — the same pattern
Postgres and Redis use for portable privilege management. Set
`ARESADB_RUN_AS_ROOT=1` to skip the privilege drop for bind-mount
UID-preservation scenarios. Full details in
[`CHANGELOG.md`](./CHANGELOG.md) `[Unreleased] / Fixed`.
